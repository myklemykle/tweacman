Hello Claude! We are going to develop some microcontroller demo projects together based on various MCUs from the Renesas RA family.

Our first project runs on the Sparkfun Thing Plus RA6M5. We're writing in Arduino and C++, and also using Faust for audio synthesis.

Our code is intended for hobbyists to learn from and extend, so it should be clear, well commented and concise, and follow Arduino conventions. We're building a series of small demo sketches - Hello World, Bluetooth, DAC audio output, potentiometer input, Faust-based synthesis - and will eventually write a tutorial from this material, so each demo should stand on its own as something a hobbyist could read and follow.

## Hardware: SparkFun Thing Plus RA6M5

- MCU: Renesas RA6M5, Arm Cortex-M33 @ 200MHz.
- Memory: 2MB code flash; ~512KB RAM; separate 8KB Data Flash region (`BSP_DATA_FLASH_SIZE_BYTES`) meant for small persistent data, not general code/heap - erased in 64-byte blocks, written in 4-byte granularity, backed by a `DataFlashBlockDevice` and reachable through the bundled `EEPROM` library. Doesn't wear-level; `EEPROM.put()`'s per-byte `update()` skips a write only when the new byte is identical to what's already there.
- Analog I/O: A0/A1 (pins 7/8) are true 12-bit hardware DACs, not PWM - `DAC`/`DAC1` in the core. A2-A5 (pins 9-12) are ADC inputs. The ADC hardware maxes out at 12 bits but `analogRead()` defaults to 10-bit scaling until `analogReadResolution(12)` is called; `analogWrite()` similarly defaults to 8-bit until `analogWriteResolution(12)` is called - both are process-wide settings, not per-pin.
- DAC output amplifier: the DAC has a real internal output amplifier that lowers its output impedance for driving an external load, but the Arduino core hardcodes it off with no exposed API. Enabling it requires reaching directly into `R_DAC`'s registers (`DAAMPCR_b`/`DAASWCR_b`/`DACR_b`) after the channel is already open - see `DACAudioTest.ino` for the working sequence and why it's a deliberate hack rather than something to build on.
- DAC signal characteristics: DAC output rides on a DC bias rather than swinging symmetrically around 0V - a series coupling capacitor (several uF) is needed between a DAC pin and any downstream audio jack/amp input to get a clean AC signal without a click at the start/end of playback.
- `LED_BUILTIN` = pin 14, the blue STAT LED. A WS2812 RGB LED is also on D13 (P105) - driven via FastLED (`FastLED.addLeds<WS2812B, 13, GRB>(...)`), see `WS2812TouchDemo.ino`. FastLED's driver for this chip masks interrupts for ~30us per LED update (longer than a 48kHz audio tick, so each update drops about one tick - measured, but inaudible) and zeroes the DWT cycle counter (`DWT->CYCCNT`), so don't time across a `FastLED.show()` with it. P105 can also be GPT1 GTIOC1A or SCI8 TXD, if the LED ever needs driving by hardware instead.
- CTSU (Capacitive Touch Sensing Unit): three real touch-capable pins on this board, decoded via this project's own `RA6M5CapTouch` library (see below) - D20 (TS05), D21 (TS04), D31 (TS11, also the onboard USR button - usable but not a great choice for a breadboard wire). All three share one analog reference pin, D6 (TSCAP), which needs an external capacitor to GND (~10nF is a good starting point) or nothing will work. See `RA6M5CapTouch.h`'s class comment for the register-level bring-up details (several real, non-obvious bugs were found debugging this from scratch against the RA6M5 Hardware User's Manual).
- `Serial` is native USB CDC, not a UART - text printed before a monitor/host opens the port is discarded outright, not buffered. Sketches should watch for the connected state to flip from false to true and (re-)greet at that point, rather than printing once in `setup()`.
- USB is the RA6M5's full-speed (12Mbit/s) port, not its high-speed one, so about 1MB/s is the practical ceiling. The core's `UsbMsd` library (the board as a USB disk) hard-codes 512-byte bulk packets, which full speed doesn't allow: linked unmodified, macOS rejects the whole configuration and the board has no serial port either - see `fixUsbDiskPacketSize()` in `SDResampleDemo/UsbDiskGate.h` for the workaround. Uploads go through DFU, not the serial port (the core's `dfu-util` detaches the board's DFU runtime interface), so `make upload` still works when the serial port is missing - unless USB never got configured at all, as with that bug; then double-press RESET to start the bootloader by hand, and flash with `dfu-util --device 0x1b4f:0x0036 -D build/<sketch>/<sketch>.ino.bin -a0 -Q`.
- SD card slot: wired to the RA6M5's native SDHI peripheral (4-bit, negotiates 50MHz High Speed), mounted through the core's `SDCardBlockDevice` + `FATFileSystem`. The core's driver has two real problems: it sends one command per 512-byte sector (reads cap at ~2.2MB/s), and it garbles data DMA'd to or from a buffer that isn't 4-byte aligned - which unbuffered `fread()`s at odd positions hit, since FatFs DMAs whole sectors straight into the caller's buffer. This project's `RA6M5FastSD` library fixes both (see below). Writes on the bench card (SanDisk Ultra 32GB) are slow regardless - ~0.35MB/s, ~25ms per 8KB. The core's FatFs is built with long filenames but code page 437, not Unicode, so only ASCII filenames are safe.
- Also on board, per SparkFun's docs but not yet used in this project: a MAX17048 fuel gauge, a 16MB external QSPI flash chip, and a Qwiic I2C connector.

## Attached peripherals (current bench setup)

- **Renesas DA14531MOD Bluetooth LE module** - on-board, a separate coprocessor from the RA6M5 itself, not a library running on the main chip. Wired to the RA6M5 over `Serial2` at 57600 baud, 8N1, no flow control. Runs Renesas' "CodeLess" AT-command firmware and advertises as `CLv2-CodeLess`. Controlled via SparkFun's unofficial `CodelessBLE` Arduino library (manually installed, not in the Library Manager). See `HelloWorldBLE.ino` for outbound-only push text (the undocumented-upstream, reverse-engineered-here GATT notify-then-read protocol) and `AudioKnobsWebBLEDemo.ino` for genuine bidirectional data - CodeLess's AT-command link has no inbound equivalent of its outbound "|" pipe convention (arbitrary writes get parsed as AT commands and rejected), so real two-way traffic needs CodeLess's separate "Binary mode"/DSPS path instead, which turns out to need the *local* UART host's active approval, not just the remote BLE central's request - see that sketch's header comment for the full handshake, and the `codeless-binary-mode-dsps-protocol` memory for the complete writeup (including phone-side WebBLE-app gotchas: Claude Artifacts can't host the companion web page at all - a Permissions-Policy blocks `navigator.bluetooth` outright - and Bluefy's `writeValueWithoutResponse()` silently drops writes, fixed by using plain `writeValue()`). Two later findings, both handled in `SDResampleDemo` and its page: Binary mode lasts exactly one connection - granted on one, active on the next, dropped by the module (which then restarts, `+READY`) when that one ends - so the page asks, hangs up and reconnects at once rather than waiting; and CodeLess's default advertising interval (~690ms) made the board take up to 20s to appear in a device picker, so the sketch sets `AT+ADVSTART=100` at boot and after every module restart. Act on the module's output only once a burst has gone quiet (~20ms) - answering mid-burst broke the handshake.
- **3.5mm TRS audio jack** - tip and ring wired to A0 and A1 (DAC0/DAC1), sleeve to GND - i.e. left and right, which is how `SDResampleDemo` plays stereo files. The right channel (A1) currently has a 4.7uF coupling capacitor for DC-blocking; the left (A0) doesn't, kept that way deliberately for A/B comparison.
- **Two Taiwan Alpha RV112FF-40 dual potentiometers** - absolute single-turn 360-degree pots, each with two wipers mechanically offset 90 degrees, giving a pair of triangle-wave signals an absolute shaft angle can be decoded from (no interrupts, no external reference needed). Confirmed via the manufacturer's own datasheet: an "endless rotary" type with no mechanical stop, rated 15,000 rotation cycles - so it really can be spun multiple times, which `MultiTurnKnob` (see below) takes advantage of. Wired: pot 1's wipers to A2/A3, pot 2's wipers to A4/A5, both pots' track ends to VREF/GND (so readings are ratiometric), with a noise-filter capacitor from each wiper pin to GND (100nF). Driven by this project's own `RV112FF` library (see below), which reports nothing until a pot's calibration is complete - a full turn after its observed range stops growing, about two turns from power-on, unless a saved calibration is restored - ported from a prior, more thoroughly-tested implementation on a different platform (Bela); see `../bela/gemtest.git` (symlinked into this repo as `gemtest.git`) for that project's own notes if the decode math or a hardware quirk needs re-deriving.
- **Two CapTouch pads** - D20 (touch1) and D21 (touch2), each just a wire or touch pad; see the CTSU note above for the shared TSCAP capacitor both depend on. In `AudioKnobsDemo`/`AudioKnobsWebBLEDemo`, touching one gates its knob's sweep speed (fast, single-turn, matching the original mapping) versus released (slow, two full turns per sweep, via `MultiTurnKnob`).
- **Onboard WS2812 RGB LED** (D13) - see the Hardware section above; driven in `WS2812TouchDemo.ino`.
- **microSD card** (SanDisk Ultra 32GB, FAT32) - see the SD note in the Hardware section. `SDResampleDemo` keeps filtered copies of each WAV it plays in a `cache/` folder on it.

## Toolchain and environment

- Arduino core: SparkFun's unofficial port of `arduino:renesas_portenta`, manually installed as a version-bumped overlay (`1.6.1`) so it takes precedence over the official `1.6.0`. This is fragile - `arduino-cli core upgrade` (or reinstalling the core) will silently wipe it, since it isn't tracked by Arduino's own board manager. Re-extract from SparkFun's core zip to recover.
- Faust 2.88.0 from Homebrew (`brew install faust`): the compiler is `/opt/homebrew/bin/faust`, its libraries and architecture headers under `/opt/homebrew/share/faust/` and `/opt/homebrew/include/faust/`. An older 2.70.3 install still sits at `/opt/faust`, later on PATH, so the Homebrew one wins. The Arduino builds use the core's own ARM gcc, so Homebrew's LLVM updates don't affect them. `make faust` regenerates `AudioKnobsDemo/synth.h`; on this chip, `-mapp` (cheaper `floor`/`fmod`) is worth passing. Faust is a poor fit for an effect called one sample at a time from the audio interrupt: its generated code re-reads and re-checks everything on each `compute()` call, so `SDResampleDemo`'s filter, written in Faust first, cost 925 cycles per stereo sample against 570 for the same maths in plain C++. First actually exercised in `AudioKnobsDemo` - see its `synth.dsp`/`faust_support.h` for the embedded-target integration pattern (a trimmed, vendored copy of Faust's own C++ architecture headers, a custom-sized wavetable to fit this chip's RAM, and a hand-rolled audio-rate `FspTimer` interrupt in place of Faust's usual audio-driver architecture files).
- Everything builds and flashes through the project `Makefile` (`arduino-cli` underneath) - see `make help`. Local libraries (`RV112FF`, `RA6M5CapTouch`, `MultiTurnKnob`, `RA6M5AnalogTuning`, `RA6M5FastSD`) are passed via `--library` rather than installed into the global sketchbook, so they stay versioned with this repo - this is also the Makefile's `LIBRARIES` default, so any new sketch gets all of them automatically. `FastLED` is a normal Library Manager install (global, not versioned with this repo).
- The core compiles with `-Os` and `-fno-builtin`; the latter turns `fabsf()`/`floorf()` into real library calls rather than FPU instructions. Hot audio code uses `__builtin_fabsf()` etc. and an `optimize("O2")` attribute instead - see `AUDIO_HOT` in `SDResampleDemo/SincInterpolator.h`.
- `FspTimer::disable_overflow_irq()`/`enable_overflow_irq()` aren't a harmless brief mask: re-enabling *clears* any interrupt that came due meanwhile, so an audio tick gets dropped. For a short critical section around audio state, use `noInterrupts()`/`interrupts()`, which just delay it.
- `tools/` holds small Python helpers with their own isolated venv (using `bleak` for Bluetooth LE): a BLE test monitor (`make ble-test`), a Binary-mode handshake tracer (`make ble-binary-test`), an end-to-end test of `SDResampleDemo`'s file management over BLE (`make ble-card-test`), `ble_upload.py` for putting files on its card over BLE (~1.8KB/s), and WAV test-file generators (`make_test_wav.py`, `make_format_test_wavs.py`). Also one C++ tool, `filter_render.cpp` (`make filter-render`), which runs `SDResampleDemo`'s `BandFilter.h` on the Mac - frequency response, self-oscillation and fade timing, or a WAV filtered for listening; it needs Homebrew's LLVM clang, since Apple's Command Line Tools here have lost their C++ headers.

## Project structure and conventions

- One sketch per feature/demo, each its own top-level folder (`HelloWorld`, `HelloWorldBLE`, `DACAudioTest`, `AudioKnobsDemo`, `AudioKnobsWebBLEDemo`, `WS2812TouchDemo`, `NoiseMeter`, `SDResampleDemo`, ...) so features can be merged together without one displacing another - see the working conventions below on how that maps to git branches. A library's own example sketches live in its `examples/` folder instead (see `RV112FF/examples/`, `RA6M5CapTouch/examples/`, `MultiTurnKnob/examples/`, `RA6M5FastSD/examples/`).
- Reusable code that more than one sketch might use gets its own library folder at the project root, structured as a normal Arduino library (`library.properties`, `keywords.txt`, `src/`, `examples/`) even though it lives in this repo rather than the global sketchbook. Current libraries: `RV112FF` (potentiometer decoding), `RA6M5CapTouch` (CTSU touch sensing on any RA6M5 board; its class is still called `CapTouch`), `MultiTurnKnob` (wraps an `RV112FF` to add Encoder-style multi-turn counting, since the pot itself is a confirmed endless-rotation part but its own sensor has no turn-counting memory), `RA6M5AnalogTuning` (one `begin()` call that sets the ADC's sampling time and discharge-before-sample, removing crosstalk between pots; a no-op on other chips), `RA6M5FastSD` (a drop-in `FastSDCardBlockDevice` for the core's SD driver: many sectors per command, and misaligned transfers bounced through an aligned buffer; experimental - it reaches into the core class's private members - and Renesas-core-only).
- A sketch with a browser-based companion UI (`AudioKnobsWebBLEDemo`, `SDResampleDemo`) keeps that page in its own `web/` subfolder, checked into this repo - it can't be published as a Claude Artifact (see the DA14531MOD note above), so it has to be self-hosted with real HTTPS somewhere the phone can reach it.
- Keep chip-specific register code out of general-purpose libraries like `RV112FF` - they should work on any Arduino with a suitable ADC. Anything RA6M5-specific goes either in a library that compiles to a no-op elsewhere (the guard is `#if defined(ARDUINO_ARCH_RENESAS) && defined(BSP_MCU_GROUP_RA6M5)`, after including `bsp_api.h` only under `ARDUINO_ARCH_RENESAS`; see `RA6M5AnalogTuning.cpp`), or in a sketch section marked `// ---- RA6M5-specific ----` / `// ---- end RA6M5-specific ----`.
- `SDResampleDemo` is the most involved sketch so far: WAV playback from SD at -1024x to +1024x, transport on the touch pads, and a BLE companion page (`web/wav-remote.html`, titled Tweacman: a status line, then tabs for the knob settings - a card per mode, editable, the board's current mode highlighted - the card's files, and diagnostics). D20 steps through the knob modes - rows of the sketch's `MODES` table (name, LED hue, a function per knob); five so far: speed mode (knob1 tape-style speed; knob2 tape scrub, which takes over the cursor while turned, with one turn fitted to a power-of-two fraction or multiple of each file) and pitch mode (knob1 the pitch you hear, relative at two octaves per turn; knob2 time-stretch, through zero - a granular freeze - and backward), and window mode (knob1 and knob2 move the start and end of the stretch of file that plays, which every other mode then treats as the whole tape; the loop lives in one mapping, `fileOffsetFor()`, and `moveVoiceWindow()` re-anchors it under a playing voice), and echo mode (knob1 delay time, knob2 one amount for level and feedback; `EchoDelay.h` - a mono, half-rate delay line in RAM, 2.7 seconds, run in the audio interrupt on every tick after the voice is rendered), and filter mode (knob1 the band's bottom cutoff, knob2 its top, MiniKorg 700 Traveler-style, each pushing the other along when they meet; `BandFilter.h` - an MS-20-flavoured resonant band-pass, a high-pass and a low-pass in series, that screams when narrowed and fades out with the echo when the transport stops; it runs just before the echo, and skips itself entirely while wide open). All knobs are relative, with a small backlash against at-rest jitter. Tapping both pads together three times resets the current file's settings to their defaults (`watchForTripleTap()`, also `RESET:ALL`); it acts on the third chord landing, so no other pad gesture waits on it. Mono or stereo, 8-32-bit PCM or float, any rate. It reads from a ladder of filtered half-rate copies it builds on the card (`MipCache`), through a windowed-sinc interpolator whose cutoff follows the read rate. Its header comment and those of its own files (`MipCache.h`, `SincInterpolator.h`, `EchoDelay.h`, `BandFilter.h`, `WavReader.h`, `RingBuffer.h`) explain the design. Each WAV's speed, pitch, window, echo and filter are saved per file in a `settings/` folder on the card (`FileSettings.h`), which also remembers the cued file across reboots. A USB disk mode (`DISK:ON`, a button on the page) hands the card to the computer on the USB cable until it's ejected there (`UsbDiskGate.h`). Each pot's calibration is saved to the Data Flash once, the first time the transport stops after it completes, and restored at boot (`CAL` shows it, `RECAL` forgets it). The Serial status line reports audio-interrupt load and dropped ticks, and a `PROFILE` command times each stage of `loop()` - keep the interrupt lean, since a CPU-heavy post-processing stage is planned. While scrubbing, the interrupt glides between control ticks' steps (`currentStep`/`targetStep`), so anything that repositions the cursor has to allow for the cursor still moving - see `startLevelChange()`. Scripted Serial tests should use the generated test WAVs (`SINE20.WAV` etc.), not real samples: per-file settings and the cued file are saved as a side effect.

## Working conventions

- If I phrase a request as "can we do such-and-such" (or similarly tentative
  phrasing), treat it as a request to discuss, not to implement. Describe
  the work as best you can - approach, what would change, what's involved -
  and stop there. Don't start coding until I explicitly ask you to proceed.

- New features should be developed on their own feature branch and merged
  in when done, rather than committed straight to main. I tend to forget
  this - when we're about to check work in, remind me to branch first if
  we haven't already.
